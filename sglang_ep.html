MoE 是什么，以及如何并行？

🎯 MoE（Mixture of Experts）：每层有 N 个专家 FFN，router 为每个 token 选 top_k 个，其余跳过。
类比：医院有 256 个专科医生，每个病人只挂 8 个号，最后按权重综合诊断。
DeepSeek V3 有 256 个 expert，单卡显存远装不下 → 必须多卡切分。两种主流方案：

TP（张量并行）

每个 expert 的权重横向切开，每张卡持有所有 expert 的一部分。

卡0: [e0前半, e1前半, ..., e255前半]
卡1: [e0后半, e1后半, ..., e255后半]

每个 token 在每张卡上都参与计算（只算半个 expert），最后 AllReduce 拼回。

EP（专家并行）

每张卡独占一批完整的 expert，权重不切。

卡0: [e0,  e1,  ..., e31]  完整
卡1: [e32, e33, ..., e63]  完整
...
卡7: [e224, ...,    e255]

问题：token 的目标 expert 可能不在自己这张卡上。

🔑 核心区别：TP 的 token 在卡间是共享的（每张卡都见到所有 token，只算自己那一片权重）；EP 的 token 原本只在某一张卡上，需要"把 token 搬到 expert 所在的卡"才能算。 👉 下一张看训练时怎么解决这个搬运问题。

训练时的 EP：2 次 All2All —— 以及 SGLang 的替代方案

🗺️ 为什么 token 要跨卡找 expert？
Token 按 batch/sequence 自然落在各 rank（t0/t1 → rank 0，t2/t3 → rank 1）。
但 router 把每个 token 路由到哪个 expert 只看语义，与 token 在哪张卡毫无关系。
结果：rank 0 的 t0 大概率同时需要 rank 0 的 e1 和 rank 1 的 e3，必须"搬"过去才能算。
🟢 SGLang 的巧妙：partial output + AllReduce
每张卡拿到全量 token（不搬 token），只计算自己持有 expert 的那份输出（partial output）。
最后一次 AllReduce(SUM) 把各 rank 的 partial output 加齐 → 完整输出。
→ 0 次 All2All，用本地 reorder kernel + 1 次 AllReduce 替代。

⚠️ 训练 vs 推理的差异：训练时 All2All 可与 backward 重叠掩盖；推理 forward 几乎无 overlap 机会，两次 All2All 的延迟直接堆到端到端 latency 上 → SGLang 用 partial output + AllReduce 方案替代。

SGLang 的解：6 步用本地 reorder + AllReduce 等价 All2All

核心想法：每张卡都拿到全量 token（不 All2All 散开） → 本地用 reorder kernel 把 token 重排成"按 expert 分段"的样子 → Group GEMM 在本地跑 → 反向 reorder + 加权 → 最后一次 AllReduce 把各 rank 的部分和加齐。

STEP 1
选专家
router 算出每个 token 的 top_k 个 expert 和权重
STEP 2
排序与建索引
按 expert id 排序，产出 3 个映射表（src2dst, seg_indptr, reorder_ids）
STEP 3
pre_reorder
本地把 token 搬到对应 expert 的连续槽 ≈ 替代 All2All ❶
STEP 4
Group GEMM ×2
w13 · SiLU · w2，按 expert 段分别批量乘（block-diagonal）
STEP 5
post_reorder
本地按原 token 顺序还原 + topk 加权 ≈ 替代 All2All ❷
STEP 6
AllReduce
跨 rank 一次 SUM，把各卡的部分加权和加齐 → 完整 output

对照训练版：Step 3 + Step 5 用本地 kernel 干了 2 次 All2All 的活儿；最后一次 AllReduce 处理跨 rank 的总和。下面用具体例子把每一步走一遍 👇

💡 整张表读作：排序后第 i 号槽位，是 token 在等 expert 处理。
例：i=0 → t1 在等 e0；i=4 → t1 又出现，在等 e2（t1 选了 e0 和 e2 两个 expert，topk=2）。
🔑 解码 reorder_ids（关键）：reorder_ids[i] 本身只是个 flat 索引 j（范围 0 ~ N·top_k−1），不直接告诉你 token。要再做一步除法：
　• token_id = reorder_ids[i] ÷ top_k　（整除 → 回到 t0~t3）
　• topk 位置 = reorder_ids[i] % top_k　（余数 → 决定用哪个 topk_weight）
　• expert = reorder_topk_ids[i]　（这个直接就是）
例：i=0，reorder_ids[0]=2 → 2÷2=1 → t1；2%2=0 → t1 的第 0 个 topk → 拿权重 0.7。
为什么要余数？同一个 token 在排序后会出现 top_k 次（如 t1 在 i=0 和 i=4 都出现），光知道"是 t1"不够，还得知道"是 t1 的第几次"才能拿对权重。

Step 2b：seg_indptr —— 每个 expert 的区间

对每个 expert id 做二分查找，找出它在排序后数组里占的范围。这是给 Group GEMM 用的 CSR 段指针。

后面 Group GEMM 一看就知道："e0 拿 0~1 这两行做矩阵乘，e1 拿 2~3 这两行……"

Step 2c：同一组工作的两种排法 —— 槽 j ⟷ 槽 i

左右是同一组 8 份工作 (token → expert)，只是排成两种顺序：
左：按 token 排（输入的自然顺序），槽号 j　·　右：按 expert 分组（GEMM 要的顺序），槽号 i
每份工作都有两个槽号 —— src2dst 和 reorder_ids 就是 j ⟷ i 的双向查询表。

💡 顺箭头读 = src2dst（搬运指令）：src2dst[j] = i，原 j 槽的工作要搬到 i 槽。
高亮那条就是 src2dst[0]=2：t0→e1 这份工作，在左边 j=0，在右边 i=2 —— 同一个 chip 两个槽号。
pre_reorder 用它"把谁写进 i 槽"；post_reorder 用它"从 i 槽读结果回来"。
🔄 反箭头读 = reorder_ids（反查）：reorder_ids[i] = j，i 槽里坐的是原 j 槽的工作。
都是"同一份工作 ↔ 两个槽号"这条事实：src2dst[j] = i ⟺ reorder_ids[i] = j。
kernel 实际只用 src2dst；reorder_ids 是 sort 顺手输出、用来"反查 i 槽里是谁"的视角。

🔁 闭环：U 形回路把所有索引串起来

🎯 具体例子：t0 经过 e1 这一圈
① src2dst[0]=2 → t0 hidden 写到槽 2 　② 槽 2 落在 e1 段 [2,4) → 走 e1 的 GEMM 　③ 结果存到 down_output[2]
④ reorder_ids[2]=0 → flat j=0 → 0÷2=t0、0%2=第 0 个 topk → weight 0.6 　⑤ out[t0] += 0.6 × down_output[2]
💎 一句话总结：src2dst 是 token 的出门地址，seg_indptr 告诉 expert "你管哪几个槽"，reorder_ids 是槽位的回家地址。三个索引一前一后，槽位夹在中间 —— 这就是 MoE 高效执行的全部秘密。
接下来三张幻灯片就是 kernel 一步步落地这条 U 形回路。

🧮 块对角性质：Group GEMM 把 gateup_input[seg_indptr[k]:seg_indptr[k+1]] 和 w13_weight[expert_k] 相乘，写到 gateup_output 对应段。
举例：gateup_output[0:2] = gateup_input[0:2] @ w13[e0]，gateup_output[2:4] = gateup_input[2:4] @ w13[e1]。每个 expert 都用自己专属的权重，互不串台。
🎁 kernel fusion 顺手做的事：FP8 路径下 pre_reorder 顺便做了输入量化、silu_and_mul 顺便做了 down_input 的 per-expert 量化 —— 不用额外多读写一遍激活。

🌟 关键：AllReduce 一次通信就把所有 rank 的部分和加齐，无需让 token 数据在 rank 间真的搬动。
每个 token 完整输出 = 它 top_k 个 expert 各自的加权贡献之和。SGLang 把这 top_k 份贡献分散在不同 rank 上各自计算，最后一次 sum 同步。

🎯 核心 trick：用 1 次 AllReduce 换掉 2 次 All2All

训练时 EP 用两次 All2All 在 rank 间搬真实 token 数据；推理时 latency 敏感、All2All 难以和计算 overlap。SGLang 改成 "每卡跑全量 token，最后做一次 AllReduce 加部分和"。

💰 动机 / 权衡 / 代价　·　动机：推理 latency 敏感，All2All 难 overlap　·　权衡：用更多 flops（每卡跑全量 reorder）+ 一次 AllReduce，换掉两次 All2All　·　代价：每张卡都开 (N × top_k, h) buffer，token 多 / EP rank 多时浪费明显 → 后续 DeepEP 用真 All2All + overlap 进一步优化

设计要点总结

设计 为什么
每张卡开全量 buffer，只写本 rank 部分 避免 token 跨卡传输，通信集中到最后一次 AllReduce
不在本 rank 的 expert 跳过 / 写零 让 AllReduce(SUM) 直接得到正确答案
seg_indptr + src2dst 两套索引 前者给 Group GEMM（段），后者给 reorder（点对点）
Pre/post reorder 顺手做量化和加权 Kernel fusion，省一次激活的读写
用 AllReduce 替代两次 All2All 推理 latency 敏感，All2All 难以 overlap

局限

  • Group GEMM 当前是 Triton 实现，FlashInfer 路径还没接通 —— 性能有上限
  • Buffer 浪费会随 EP rank 数 / batch 增大而变明显
  • 后续 DeepEP 用真正的 All2All + overlap 做了进一步优化

The End
