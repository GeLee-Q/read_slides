Part 1 — MoE 背景

为什么需要 MoE？— Dense vs MoE 对比

参数量 vs 激活量的困境，条件计算思想

Dense 模型的困境
  • 模型越大效果越好，但计算成本随参数量线性增长
  • GPT-3 175B：每 token 激活所有参数 — 极其昂贵
  • 扩大参数量 = 直接扩大 FLOPs 开销
条件计算（Conditional Computation）
  • 核心洞察：不同 token 需要不同"专长"
  • 每个 token 只激活一小部分参数
  • 参数量↑ 但 FLOPs 不变 → 更高效的扩展
MoE 价值主张：用 8× 参数量达到 Dense 效果，每步仅激活 1/8 的专家

Part 1 — MoE 背景

Expert 是什么？& Top-K 路由机制

Expert = FFN，门控路由决定每个 token 的计算路径

Expert 的本质
  • Expert = 标准 FFN（两个线性层）
  • Linear(d_model → ffn_hidden)
  • Linear(ffn_hidden → d_model)
  • 每个 token 仅激活 top-K 个 expert（K=2）
# Megatron-LM MoE 关键参数 --num-experts 8 # Expert 总数 --moe-router-topk 2 # 每 token 激活 K 个 --moe-ffn-hidden-size 4096 # Expert FFN 宽度 --moe-shared-expert-intermediate-size 2048 # 共享专家（始终激活）
Shared Expert：永远激活，不参与路由，处理通用语义；路由专家处理特化信息
Part 1 — MoE 背景

专家崩溃与辅助负载均衡损失

L_aux 通过同时惩罚"实际偏斜"与"期望偏斜"，迫使路由趋向均匀

专家崩溃（Expert Collapse）
  • 训练初期某 expert 偶然获得更多 token
  • 梯度更新让它变"更强"→ 吸引更多 token → 恶性循环
  • 最终退化：所有 token 只去一个 expert = Dense FFN
辅助负载均衡损失 L_aux
Laux = α · Σi fi · Pi
fᵢ — 实际负载
该 expert 实际接收的 token 比例
= routing_map.mean(dim=0)
Pᵢ — 期望负载
router 分配给该 expert 的平均概率
= scores.mean(dim=0)
关键洞察：fᵢ 和 Pᵢ 同时偏高（同一 expert 主导）时，乘积最大，损失最高 → 梯度反向推均匀化
均匀时：L_aux = N · (1/N)·(1/N) = 1/N（最小）
崩溃时：L_aux → fmax·Pmax ≈ 1（最大）
# router.py: aux_loss_func() tokens_per_expert = routing_map.float().mean(dim=0) # fᵢ：每个 expert 实际接收的 token 比例 [num_experts] router_prob_per_expert = scores.mean(dim=0) # Pᵢ：router 分配给每个 expert 的平均概率 [num_experts] aux_loss = dot(tokens_per_expert, router_prob_per_expert) # 最终损失 = α · Σ(fᵢ·Pᵢ)，加入总 loss
Part 2 — Expert Parallelism 概念

EP 核心思想：分专家，不分矩阵

完整 Expert 分散在不同 GPU；Token 通过 All-to-All 精准送达目标 Expert

核心公式
num_local_experts = num_experts / EP
num_experts = 8 EP = 4 每 GPU 2 个 Expert
EP 不切单个 Expert 的权重，而是把完整 Expert分散到不同 GPU； Token 被 router 选中后，再通过 All-to-All 送到 Expert 所在 rank。
8 Experts × EP=4 的实际落位
为什么 MoE 优先选 EP
TP 用在 MoEEP 用在 MoE
每个 expert 的 GEMM 后都要 AllReduce只交换被路由到 expert 的 token
expert 被切碎，小矩阵导致 GPU 利用率差每卡保留完整 expert，矩阵形状更友好
通信量随 expert 数量增长通信量主要由 top-k 稀疏度决定
GroupedGEMM：把“多专家小批量”重新拼回大计算
# 传统：N 次独立 GEMM（N 次 kernel 启动，高开销） for i in range(num_experts): output[i] = torch.mm(tokens_for_expert_i, W[i]) # GroupedGEMM：1 次 kernel 处理所有 expert（experts.py） output = grouped_gemm(all_tokens, all_weights, tokens_per_expert) # 单次 kernel 调用，充分利用 GPU SM，减少调度开销
通信侧：All-to-All 解决“token 去哪张卡”
计算侧：GroupedGEMM 解决“到卡后怎么算得快”
一句话结论：TP 是“把一个矩阵切给多卡”，EP 是“把多个完整 expert 分给多卡”，后者更贴合 MoE 的稀疏路由本质。
Part 3 — Token 路由

Gate 网络 → Routing Map：Token 路由完整流程

线性投影 → Softmax/Sigmoid → Top-K 选取 → routing_map [S×E] 布尔矩阵 → All-to-All 触发

Gate 路由决策 — 4 步详解
  • ① 输入：hidden_states [S, d_model]
    S = 序列长度；d_model = 隐向量维度
  • ② 线性投影：W_gate [d_model, E] → logits [S, E]
    W_gate 无 bias；把 token 映射到 E 个 Expert 的打分空间
  • ③ 归一化 → scores [S, E]
    Softmax：全局竞争，各行和 = 1
    Sigmoid：各 Expert 独立打分
  • ④ Top-K 选取：每 token 保留最高分的 K 个 Expert 位置
    K=2 → 每 token 激活 2 个 Expert，FLOPs ≈ Dense 的 25%
  • 输出：routing_map [S, E]（布尔矩阵，每行恰好 K 个 True）
TopKRouter 核心代码
# moe/router.py: TopKRouter.forward() logits = self.gate(hidden_states) # [S, d_model] → [S, E] 原始打分 scores = softmax(logits, dim=-1) # [S, E] 归一化，各行和 = 1 top_scores, top_idx = topk(scores, K) # [S, K] Top-K Expert 值与索引 routing_map = build_routing_map(top_idx, E) # [S, E] bool，True = 路由目标
routing_map [4 tokens × 8 experts] · 每行恰好 K=2 个 T；T = 路由到该 Expert，F = 不路由
Part 4 — Token Dispatch via All-to-All

All-to-All：把 Token Copies 定向送到目标 Rank

Permute 之后，每张卡都像在“按目标 GPU 分拣快递”一样，把 token copies 定向发往需要它们的那张卡；图中 T0-T3 只是示例，不代表固定绑定某张 GPU

All-to-All 的核心语义
  • 每个源 rank 只发送目标 expert 真正需要的 token copies
  • 同一个 token 可以同时发往多个目标 rank
  • 同一个目标 rank 也会从多个源 rank 接收 token copies
  • 它是 many-to-many 的定向交换，不是把所有 token 广播给所有人
Megatron 实际使用：All-to-All-v
  • 不同目标 rank 的分片长度通常不同
  • 通过 `input_split_sizes` / `output_split_sizes` 描述每段长度
  • 发给自己 GPU 的那段保留本地，可视作“不出站”的本地分片
  • 通信量主要取决于 top-k 稀疏路由，而不是 expert 总数
发送前：每张卡只保留“待发 token copies”

Step 1：Permute（排列）

按目标 EP rank 重排 token 内存布局 — moe_utils.py: permute()

为什么要 Permute？
  • all_to_all_single 要求发送数据在内存上连续
  • 需要将"发给 GPU 0 的 token"连续排列，再是"发给 GPU 1"...
  • 同时计算 input_splits：每段有多少 token

Memory View

Part 5 — 通信策略对比

三种 Dispatcher 对比

AllGather / AlltoAll / Flex — 适用场景各有侧重

Dispatcher通信原语特点适用场景
AllGather AllGather + local scatter 广播所有 token，实现简单；通信量大但拓扑友好 小规模 EP，NVLink，token 分布均匀
AlltoAll All-to-All-v × 2 精准路由，只通信必要 token；需要 permute/unpermute 标准 EP，跨节点大规模，稀疏路由
Flex DeepEP 融合算子 permute + A2A + unpermute 融合为更少 kernel；支持 HybridEP 超大规模 EP，追求极致延迟
AllGather Dispatcher 流程
① AllGather → 所有 GPU 得到完整 token 集
② 本地按 routing_map 提取对应 expert token
③ 本地 Expert 计算（无跨 GPU A2A 开销）
④ ReduceScatter → 聚合输出
AlltoAll vs AllGather 选择
  • top-K 稀疏（K=2, 8 experts）→ A2A 通信量约 25%，优选 AlltoAll
  • EP 在节点内 + NVLink → 可选 AllGather
  • AllGather 通信量固定为 batch × d_model × EP，不受稀疏性影响
Part 5 — 通信策略对比

Flex Dispatcher：DeepEP & HybridEP

融合 permute + A2A + unpermute，消除 CPU 调度瓶颈 — fused_a2a.py

DeepEP 的关键创新
  • 来自 DeepSeek 开源的 EP 专用通信库
  • 将 permute + all_to_all + unpermute 融合为更少 CUDA kernel
  • 消除 CPU 调度多个 kernel 的延迟
  • 支持异步通信：通信与计算重叠

  • 节点间（InfiniBand）：高带宽 AlltoAll
  • 两层路由，最大化硬件利用率

Part 6 — 关键优化

负载均衡优化

核心矛盾：热门 expert 过载、冷门 expert 闲置；目标是在稳定训练的同时，把 token 更均匀地摊到各专家

先看问题：为什么会失衡？
  • router 初期会偏爱少数 expert，导致热门专家持续吸走更多 token
  • 热门 expert 越忙，队列越长；冷门 expert 越闲，GPU 利用率越差
  • 所以负载均衡的核心不是“绝对平均”，而是避免局部过载和长尾空转
手段 1：Capacity Factor（硬上限）
capacity = ⌊S × top_k / E × capacity_factor⌋
  • 给每个 expert 设一个“最多接多少 token”的容量上限
  • capacity_factor > 1.0：允许轻微过载，避免上限太死
  • 超过容量的 token 会被 drop 或延后，是稳定性和利用率之间的硬性权衡
手段 2：Expert Bias（软调节）
routing_score = logit + bias[expert]
  • 不是直接拦截 token，而是提前改写 router 打分，调节“谁更有吸引力”
  • 负载高的 expert：bias 下降，后续 token 更不容易继续涌入
  • 负载低的 expert：bias 上升，把后续 token 慢慢引导过来
  • 优点是连续、在线、对主梯度干扰小，所以 DeepSeek-V3 更偏爱这种方案
一句话理解：Capacity Factor 是“别再进来了”的硬闸门，Expert Bias 是“下一个别总来这边”的软引导；两者都在解决热门 expert 过载。
Bias Rebalance
Expert Bias 是怎么把负载拉回来的？ 它不是事后惩罚，而是在 router 打分阶段就做“削峰填谷”：热门 expert 降吸引力，冷门 expert 升吸引力。
Part 6 — 关键优化

Token 排列融合优化

moe_permute_fusion / moe_router_fusion / TE Fused Kernels

moe_permute_fusion
  • 将 permute + dropout + bias-add 融合为单 kernel
  • 减少显存读写次数（避免中间 tensor 写回）
  • 配置：--moe-permute-fusion
moe_router_fusion
  • 将 router linear + softmax + topk 融合
  • 减少 router 计算延迟（通常仅 <1ms）
  • 配置：--moe-router-fusion
TE Fused MoE Kernels
  • TransformerEngine 提供 FP8 GroupedGEMM
  • FP8 量化 + fused GeLU + GroupedGEMM
  • 适合 H100 等支持 FP8 的 GPU
grouped_gemm_util.py
  • 封装 TE GroupedGEMM 接口
  • 有 TE → FP8 GroupedGEMM；无 TE → fallback 循环
  • 训练性能的关键路径
