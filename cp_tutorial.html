Section 1 · 为什么需要 CP？

128K token 序列，Attention 矩阵有多大？

计算复杂度

Self-Attention 对序列长度 S 的复杂度：

O(S²)

为什么是 O(S²)？
每个 token 要和所有其他 token 算一次相似度（Q × Kᵀ），共 S × S 次乘法。

S = 128 000 → 矩阵有 128K × 128K = 164 亿个元素

显存占用逐步推导（bfloat16）

张量形状大小
Q / K / V（各） [S, H, D] 128K×64×128×2B ≈ 2.1 GB
Attention Score（单头） [S, S] 128K×128K×2B ≈ 32 GB
一张 H100 上限 — 80 GB
2B 是什么？ bfloat16 = 脑浮点16位，每个数占 2 字节（Bytes）。
单头 Score 为何 32 GB？ 每个 Q-token 要对所有 128K 个 K-token 算一个分数 → 矩阵是 128K × 128K 的方阵。
加上权重 + 梯度 + 优化器 → 单卡根本装不下。

内存随序列长度增长（示意）

结论：128K 场景下 Attention 矩阵远超单卡显存。
→ 需要把序列维度切开，分摊给多张 GPU。
→ 但 Causal Attention 要求每个 token 看到所有历史 KV——切开后如何拿到全局 KV？见第 5 页详解。

② Causal Attention 是什么？

自回归语言模型一次生成一个 token：预测第 t 个词时，第 t+1、t+2… 个词还不存在，所以规定每个 token 只能 attend 自身及更早的位置。

实现上：Attention 矩阵的上三角强制填 −∞，softmax 后变 0，等于屏蔽未来信息。

行 = Query token（当前处理）

列 = Key token（历史）

■ 蓝格 = 可 attend（自身或更早）

□ 灰格 = 屏蔽（未来，填 −∞）

结果：下三角矩阵

③ 切序列后为什么出问题？

每个 rank 只有自己那段的 K/V。但 Causal Attention 要求靠后的 token（Rank 3）attend 所有更早的 K/V（在 R0/R1/R2 上）。

解决方向：All-Gather KV
在 Attention 计算前先通信 K 和 V，让每个 rank 临时持有全局 KV，再做 Q_local × K_globalT。
详细的 3 步计算流程见第 5 页（Q 为何不需要 gather？峰值显存注意事项？）
为什么叫"Causal"（因果）？
因为它模拟了因果关系：第 t 个词只能被它之前的词"影响"，不能被未来的词影响。这与传统 BERT 的双向 attention 不同。

Section 2 · 分布式训练基础

3 种通信原语：All-Gather / Reduce-Scatter / All-Reduce

All-Gather

各 rank 贡献一段，最终所有 rank 拥有完整数据。

Reduce-Scatter

先对各 rank 求和（Reduce），再分段分发（Scatter）。

All-Reduce

= All-Gather + Reduce。所有 rank 都得到全局求和结果。

口诀：All-Gather = 每人都有全部；Reduce-Scatter = 各拿一段汇总；All-Reduce = 每人都有全部汇总。
CP 前向用 All-Gather（收集 K/V，见第 5 页），反向用 Reduce-Scatter（分散 dK/dV 梯度），logit 重建用 All-Reduce。

Section 1 · 为什么需要 CP？

CP 中的 Attention 计算：本地投影 → All-Gather KV → 本地 Q × 全量 KV

① 本地线性投影（无通信）

每个 rank 只看自己的隐状态 h_local [S/cp, H, d]，用共享权重 W 投影：

Q_local = h_local @ W_q  # [S/cp, H, d]
K_local = h_local @ W_k  # [S/cp, H, d]
V_local = h_local @ W_v  # [S/cp, H, d]

权重 W_q/W_k/W_v 各 rank 完全一致——这是 CP 与 TP 的本质区别。

② All-Gather K 和 V（Q 不 Gather）

为满足 Causal Attention 的跨序列依赖，K 和 V 需要汇聚全量；Q 无需 gather：

K_global = all_gather(K_local)  # [S, H, d]
V_global = all_gather(V_local)  # [S, H, d]
# Q_local 不变，无需 gather

通信量 ≈ 2 × (S/cp) × H × d × (cp−1)/cp。cp 越大，每卡通信量越少。

⚠ 概念简化：此处用 All-Gather 说明原理。实际默认路径（TE，cp_comm_type="p2p"）使用 Ring P2P 分步传递，总通信量等价但峰值内存更低。

③ 本地 Q × 全量 KV → 本地 Output

scores    = Q_local @ K_global.T / sqrt(d)
            # [S/cp, S]
scores    = apply_causal_mask(scores)
out_local = softmax(scores) @ V_global
            # [S/cp, H, d]

各 rank 独立计算，无额外通信。Attention 矩阵从 [S,S] 降至 [S/cp, S]——节省 cp 倍激活显存。

4-rank 数据流（cp=4，每 rank 持 S/4 token）

直觉：为什么各 rank 只算本地就够了？
Attention 核心公式：token i 的输出  output[i] = Σⱼ softmax( Q[i] · Kⱼᵀ / √d ) · Vⱼ
注意：只用了 Q[i]（token i 自己的 query），对所有 j 求和时用的是全量 K/V，但 完全不涉及其他 token 的 Q。
所以 rank 2 只需拿自己的 Q_local，再 all-gather 来全量 K/V，就能独立、正确地算出自己那段的 output——和在单卡上对完整序列做 attention 结果完全一致。
Q 不 gather 的原因：rank 2 的 Q 只给 rank 2 自己用，没有任何别的 rank 需要它，gather 了纯粹是浪费带宽。

FlashAttention 按 Block 跳过全 masked 块：
FlashAttention 把矩阵切成若干块逐块处理。若某块所有格子都是 −∞，该块的 matmul 被直接跳过，不消耗任何 FLOPS。

R3： 几乎无全 masked 块 → 4 个 block 几乎全算 → 全力运行

一句话：K_global 对所有 rank 都是同样大的 16 列，但 Causal Mask 决定"你真正需要算哪些列"——越靠后的 rank，历史越长，有效列越多，FlashAttention 越少能跳过，算得越重。

Section 3 · Zigzag Ring Attention

Zigzag 切分：每 rank 取首尾对称两段，Causal 矩阵面积天然均衡

核心公式

把序列分成 2 × cp_size 个 chunk，

Rank r 取第 r 块（头部）+ 第 2N-r-1 块（尾部）。

4 rank × 8 token（chunk_size = 1）

Rank头部 chunk_0尾部 chunk_1有效格
R0tok 0tok 71+8 = 9
R1tok 1tok 62+7 = 9
R2tok 2tok 53+6 = 9
R3tok 3tok 44+5 = 9
为什么均衡？
头部 token 序号小 → causal 有效格少（轻）；
尾部 token 序号大 → causal 有效格多（重）。
轻 + 重 = 每 rank 有效格恰好相等。
对比朴素切法（上一页）：R0 仅 10 格，R3 达 58 格，差距 5.8×。
Zigzag 让每 rank 都持有"早段＋晚段"，完全消除失衡。

Causal 注意力矩阵（8 token）：行 = Q token，列 = K token，彩色 = 有效计算，灰色 = Mask

每个 rank 恰好 9 个有效格（= 总有效格 36 的 25%）；每行行号越大有效格越多，Zigzag 让"大行"与"小行"配对，完美抵消。

def slice_with_cp(tokens, pad_value, qkv_format="thd", max_seq_len=None): cp_rank = mpu.get_context_parallel_rank() cp_size = mpu.get_context_parallel_world_size() if cp_size == 1: return tokens # 单卡直通 token_len = len(tokens) # bshd 用 max_seq_len 统一 batch 内 chunk 边界，thd 用 token_len tlen = max_seq_len if qkv_format == "bshd" else token_len # ① chunk_size（向上取整，保证 2N 块能整除序列） chunk_size = (tlen + 2*cp_size - 1) // (2 * cp_size) # ↑ cp_size=4, tlen=16 → chunk_size=2，序列分成 2×4=8 块 # ② pad 到 2×cp_size×chunk_size 的整数倍 tokens = pad_tokens(tokens, 2*cp_size*chunk_size - token_len) # ③ 头段：chunk 索引 = r，从序列前端取第 r 块 start_1, end_1 = (chunk_size * cp_rank, chunk_size * (cp_rank + 1)) # R0:ck=0,tokens[0:2]=[0,1] R1:ck=1,[2:4]=[2,3] # R2:ck=2,tokens[4:6]=[4,5] R3:ck=3,[6:8]=[6,7] # ④ 尾段：chunk 索引 = 2N-r-1，从序列后端对称取第 r 块 start_2, end_2 = (chunk_size * (2*cp_size - cp_rank - 1), chunk_size * (2*cp_size - cp_rank)) # R0:ck=7,tokens[14:16]=[14,15] R1:ck=6,[12:14]=[12,13] # R2:ck=5,tokens[10:12]=[10,11] R3:ck=4,[ 8:10]=[ 8, 9] # ⑤ cat → 每 rank 持有 2×chunk_size 个 token，输出： # R0→[0,1,14,15] R1→[2,3,12,13] R2→[4,5,10,11] R3→[6,7,8,9] return torch.cat([tokens[start_1:end_1], tokens[start_2:end_2]])

cp_size=4, token_len=16 → chunk_size=2，序列分为 2×4=8 块

核心对称性：头块索引 r + 尾块索引 2N-r-1 = 2N-1（常数）。 所以 R0 取最前＋最后，R3 取正中间两块——正好是 Causal 矩阵里轻重互补的行对。

Section 4 · AllGather CP 模式（DSA 模型）

DSA 模型为何不能用 Zigzag？→ 改用 AllGather-CP

什么是 DSA？

DeepSeek-V3.2 / GLM-5.1 等模型使用稀疏 Attention 或非标准 Causal Mask。

Zigzag 的负载均衡基于"标准下三角 Causal"假设——DSA 打破这个假设，导致负载再次失衡。

AllGather-CP 数据流（data.py L76–94）

if allgather_cp: # ① concat 所有序列（全局） tokens = torch.cat(tokens, dim=0) # ② pad 到 cp_size × pad_size 的整数倍 global_pad_size = cp_size * pad_size pad = (global_pad_size - tokens.size(0) % global_pad_size ) % global_pad_size tokens = F.pad(tokens, (0, pad), ...) # ③ 等分切割，每 rank 取第 cp_rank 段 tokens = tokens.chunk(cp_size,dim=0)[cp_rank]
AllGather-CP 额外问题：
其 logit 布局是连续的，但 slime 的 loss 计算假设 Zigzag 布局。
→ 需要 _allgather_cp_redistribute() 做布局转换。
原理：稀疏填充 + all_reduce = 全局重建 → 重新 zigzag 切片。
一句话总结：
Zigzag 针对标准 Causal 优化了负载均衡；
AllGather-CP 是非标准 attention 模型的兜底方案。

所有 slime 模型（qwen3、hf_attention 等）均硬编码 cp_comm_type="p2p"，由 TE 执行 Zigzag Ring Attention。

Ring Attention（P2P）：KV 沿环传递，像流水线一样计算

核心思路（类比流水线传菜）

N = CP size（即参与 CP 的 GPU 数，如 4）

  • 每个 rank 只拿自己那份 KV（1/N，zigzag 切分）
  • 共 N 轮：每轮 接收上家的 KV → 计算 Q × K → 把 KV 传给下家
  • 接收和计算同时进行（P2P 异步 + 双缓冲）
  • online softmax 跨轮累积，最终合并成完整 attention 输出

Zigzag 切分保证每轮计算量均衡

causal attention 矩阵里，早期 token 的有效格子少（上三角左上角），晚期 token 多（右下角）。

Zigzag：每 rank 同时拿序列首段 + 尾段（对称）→ 两段合并后每轮有效计算量近似相等 ✓

与 All-Gather CP 对比

All-Gather CPRing P2P ✓
总 FLOP相同（Q_local × 全局 KV）
总通信量相同（(N-1)/N × KV_total）
overlap 方式 按 head 组流水
gather head[i+1] ∥ 算 head[i]		 按 CP chunk 流水
recv KV[k+1] ∥ 算 KV[k]
Attn score 矩阵
长序列内存瓶颈		 S_local × S_global

Section 6 · Megatron 4 种 CP 通信模式

Ulysses（All-to-All）：换一个维度切——分 Heads 而非分 KV

核心流程（N = CP size）

A2A 前：每 rank 有 S/N token，全部 H heads
↓ All-to-All ← 本质是分布式转置
分片轴：token 维度 → head 维度
[N × S/N × H] ⟹ [N × S × H/N]
A2A 后：每 rank 有全部 S token，H/N heads → 独立做完整 attention
↓ All-to-All（逆转置还原）
分片轴：head 维度 → token 维度
输出恢复 S/N token 格式，结果与单卡完全一致

为什么按 head 切是合理的？—— 头间独立性

Head_i = Softmax( Q_i · K_iT / √d ) · V_i
  • 每个 head 只用自己的 Q_i, K_i, V_i——不同 head 间零数据依赖
  • Rank 0 持有全序列 × H0,H1 → 独立算出 H0,H1 的正确结果
  • Rank 1 持有全序列 × H2,H3 → 独立算出 H2,H3 的正确结果
  • 拼合两份输出 = 与单卡完整计算数学等价
对比 Ring：按 token 切，softmax 需要全局 K,V（跨 token 依赖）→ 必须环形传 KV

限制 & slime 状态

  • H 必须能被 cp_size 整除
  • GQA 下 KV head 数少，某些 rank 可能拿不到 KV head
  • 通信量大，仅适合 NVLink 节点内，不适合跨节点 IB
  • slime：未启用（cp_comm_type="a2a" 均未使用）

Section 6 · CP 通信模式

分层 CP：A2A 在节点内、P2P 跨节点——为何这样分工？

三步执行流程

①
节点内 A2A（NVLink ≈900 GB/s）
节点内 cp_inner 个 GPU 做 All-to-All：token 维度 → head 维度，各 GPU 换到本节点全部 tokens × 仅 1/cp_inner heads
②
跨节点 P2P Ring（IB ≈400 Gb/s）
cp_outer 个节点之间做环形 KV 传递，仅需 cp_outer − 1 = 1 轮 IB 通信即可完成全局 attention
③
节点内逆 A2A（NVLink）
head → token 维度，还原原始 token 布局，结束本轮 attention

与纯 P2P Ring 对比（总 CP = 16）

方案IB 轮数NVLink 轮数
纯 P2P Ring15 轮0
分层 A2A + P2P1 轮2（A2A）

→ IB 通信量减少约 93%，NVLink 高带宽承担高频小数据

节点内 A2A 把 16 GPU 的大环"压缩"成 2 组，IB 只需 cp_outer−1 次——每新增一个节点仅多 1 轮 IB，而非多 cp_inner 轮。

Section 7 · 完整流程总结

常见陷阱与使用提示

① Loss 缩放
CP 把序列切成 1/N，每 rank 的 loss 项变少。需要在 sum_of_sample_mean 中正确聚合，或在 loss 后乘以 cp_size。
② cu_seqlens × cp_size（虚拟序列长度）
thd 格式下，FlashAttention 用 cu_seqlens 构建 Causal Mask，需要知道原始完整序列长度，乘以 cp_size 才正确。
③ AllGather-CP 仅限 DSA 模型
普通 Causal LM 使用 --allgather-cp 会导致负载失衡，最差可达 N:1 的计算差异。
④ 空 rank 梯度死锁
某 rank 的 chunk 完全落在 prompt 区时，logit 贡献为 0。必须保留 0 × logits.sum() 路径让该 rank 参与 all_reduce，否则集体通信死锁。
⑤ unconcat_tokens 必须保留
Loss 的 prompt/response 边界计算依赖原始全局索引，切分后无法重建。batch["unconcat_tokens"] 在 get_batch() 第一步保存，不能删除。
⑥ 前向 / 反向对称性
All-Gather KV（前向）的数学伴随恰好是 Reduce-Scatter dKV（反向）。自定义 attention 时必须手动保证这一对称性，否则梯度错误。

CP 场景下，每个 rank 只持有 response 的一部分（两段 zigzag chunk 中与 response 相交的部分）。

直接对本地 loss 求均值会得到错误结果，因为分母（response 总 token 数）是全局的，不是本地的。
