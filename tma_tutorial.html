🚀 什么是 TMA？

TMA 是 NVIDIA Hopper 架构（H100 GPU）引入的新硬件单元，全称 Tensor Memory Accelerator（张量内存加速器）。它的核心作用只有一件事：

一句话理解 在 GPU 的 全局内存（GMEM） 和线程块的 共享内存（SMEM） 之间异步地搬运数据。TMA 的关键优势在于：地址和步长等辅助信息通过 TMA 描述符以单线程方式处理，既节省寄存器，也自动处理越界检查（predication）。
GPU 内存层次示意
🗄️ 全局内存 GMEM
容量大，速度慢
所有线程块共享
→ TMA Load ← TMA Store
⚡ 共享内存 SMEM
容量小，速度快
线程块内部共享
TMA 通过描述符以单线程方式处理地址和步长，节省寄存器并自动处理越界

TMA 带来了什么好处？

传统方式搬数据时，每个线程都得自己算地址、自己发请求，很费寄存器也很繁琐。TMA 的优势：

  • ✅ 异步：发出搬运命令后，GPU 的其他线程可以继续干活，数据在后台加载
  • ✅ 省寄存器：地址和步长信息打包在「TMA 描述符」里，不占运行时寄存器
  • ✅ 自动越界检查：不需要手写边界判断代码，TMA 硬件自动处理
  • ✅ 单线程发令：一个线程负责发出 TMA 命令，其他线程只需等待完成

整体工作流程（两步走）

  1. 主机端（Host）：创建 TMA 描述符（tma_load 或 tma_store 对象），描述要搬什么、从哪搬、搬到哪里的格式
  2. 设备端（Kernel）：在 GPU kernel 里用这个描述符发起实际的数据搬运，配合同步机制等待完成

📥 TMA Load：把数据加载到共享内存

TMA Load 的方向是：GMEM → SMEM（全局内存 → 共享内存）。

第一步：主机端代码（创建 TMA 对象）

关键思路 在 CPU 上提前「打包好搬运计划」，然后把这个计划传给 GPU kernel 执行。 
template <typename T, int CTA_M, int CTA_N>
void host_fn(T* data, int M, int N) {
  using namespace cute;

  // 1. 描述全局内存（GMEM）里矩阵的形状和排列方式（行主序）
  auto gmem_layout = make_layout(make_shape(M, N), LayoutRight{});
  auto gmem_tensor = make_tensor(make_gmem_ptr(data), gmem_layout);

  // 2. 描述共享内存（SMEM）的形状（每块线程块存多大的块）
  auto smem_layout = make_layout(make_shape(CTA_M, CTA_N), LayoutRight{});

  // 3. 创建 TMA Load 对象（把上面两个信息打包成描述符）
  auto tma_load = make_tma_copy(SM90_TMA_LOAD{}, gmem_tensor, smem_layout);

  // 4. 启动 GPU kernel，把 tma_load 传进去
  tma_load_kernel<CTA_M, CTA_N>
      <<<dim3{M/CTA_M, N/CTA_N, 1}, 1>>>
      (tma_load, gmem_tensor);
}
注意 make_tma_copy 在幕后创建了一个 CUtensorMap（TMA 描述符）。这个对象存储了所有地址和步长信息，传给 kernel 后 GPU 硬件会自己根据它来访问内存，不需要每个线程单独计算。

第二步：设备端代码（在 Kernel 里执行加载）

template <typename T, int CTA_M, int CTA_N, class TmaLoad, class GmemTensor>
__global__ void tma_load_kernel(
        __grid_constant__ const TmaLoad tma_load,  // ← 必须加这两个修饰符
    GmemTensor gmem_tensor) {

  using namespace cute;
  // 要搬运的字节数
  constexpr int tma_bytes = CTA_M * CTA_N * sizeof(T);

  // 共享内存：存数据 + 存同步用的屏障
  __shared__ T        smem_data[CTA_M * CTA_N];
  __shared__ uint64_t tma_mbar;           // 异步屏障（mbarrier）

  auto smem_tensor = make_tensor(make_smem_ptr(smem_data),
                        make_layout(make_shape(CTA_M, CTA_N), LayoutRight{}));

  // ★ 只有线程 0 负责发出 TMA 命令
  if (threadIdx.x == 0) {
    // 获取 GMEM 的坐标视图，并切出本线程块对应的那块
    auto gmem_coord     = tma_load.get_tma_tensor(shape(gmem_tensor));
    auto gmem_coord_cta = local_tile(gmem_coord,
                              Tile<Int<CTA_M>, Int<CTA_N>>{},
                              make_coord(blockIdx.x, blockIdx.y));

    // 初始化屏障（1 个线程到达即触发）
    initialize_barrier(tma_mbar, 1);

    // 告诉屏障"我预计会有这么多字节写入完成"
    set_barrier_transaction_bytes(tma_mbar, tma_bytes);

    // 发出 TMA Load 命令：从 GMEM 的坐标块 → SMEM
    auto tma_per_cta = tma_load.get_slice(0);
    copy(tma_load.with(tma_mbar),
         tma_per_cta.partition_S(gmem_coord_cta),   // 源：GMEM 的坐标
         tma_per_cta.partition_D(smem_tensor));      // 目标：SMEM
  }

  __syncthreads();                        // 所有线程先同步
  wait_barrier(tma_mbar, 0);            // 所有线程等待 TMA 完成

  // ✅ 到这里，数据已经完整加载进 smem_data
}

理解「异步屏障（mbarrier）」

TMA Load 是异步操作，发出命令后数据还没到。我们需要一种机制来知道「数据什么时候到了」。这就是 mbarrier 的作用：

mbarrier 生命周期：phase 在 0 和 1 之间交替翻转——第一次以 phase=0 等待，完成后自动翻转为 1；下次复用 mbarrier 时以 phase=1 等待，再次翻转回 0，如此循环

Phase 翻转意味着所有预期字节都已写入 SMEM，此时 wait_barrier 返回
1

2
设定预期字节数 set_barrier_transaction_bytes(tma_mbar, tma_bytes) — 告诉屏障「我预计 N 字节会被写入 SMEM」，同时线程 0 「到达」屏障
3
发出 TMA 命令 copy(...) — TMA 硬件开始在后台搬运数据。每搬完一字节就向屏障报告
4
所有线程等待 wait_barrier(tma_mbar, 0) — 线程休眠，直到屏障的 phase 从 0 翻转到 1，代表所有数据已到达 SMEM
为什么 wait_barrier 之前要有 __syncthreads()？ 所有线程都要调用 wait_barrier，但只有线程 0 在 if 块里执行了 arrive-on 操作。__syncthreads() 在此是必要的，用来解决 if 块造成的线程发散（thread divergence），让所有线程重新汇合，之后才能一起调用 wait_barrier。

关于边界和对齐要求

16 字节对齐限制 TMA 要求 GMEM 张量的非连续方向步长必须是 16 字节的倍数。以 float（4 字节）为例：行主序矩阵的行步长（即列数 n）必须满足 n % 4 == 0。如果不满足，需要对输入矩阵补齐（padding）。

好消息是：不需要手写边界判断！即使矩阵大小不是 CTA_M/CTA_N 的整数倍，TMA 硬件会自动跳过越界访问，安全处理余数块。

📤 TMA Store：把数据写回全局内存

TMA Store 的方向是：SMEM → GMEM（共享内存 → 全局内存），和 Load 方向相反。

📥 TMA Load

  • 方向：GMEM → SMEM
  • 同步：异步屏障（mbarrier）
  • 同步时机：操作之后等待
  • 单线程发令：是

📤 TMA Store

  • 方向：SMEM → GMEM
  • 同步：代理围栏（proxy fence）
  • 同步时机：操作之前同步
  • 单线程发令：是

完整代码示例

template <typename T, int CTA_M=32, int CTA_N=32>
__global__ void tma_store_kernel(
    __grid_constant__ const TmaStore tma_store,
    GmemTensor gmem_tensor) {

  using namespace cute;
  __shared__ T smem_data[CTA_M * CTA_N];
  auto smem_tensor = make_tensor(make_smem_ptr(smem_data),
                        make_layout(make_shape(CTA_M, CTA_N), LayoutRight{}));

  // 第一步：各线程把数据写入共享内存（每行填入行号）
  for (int j = 0; j < CTA_N; ++j)
    smem_data[threadIdx.x * CTA_N + j] = threadIdx.x;

  __syncthreads();    // 等所有线程都写完 SMEM
    tma_store_fence();  // ← 关键！确保 SMEM 写入对 TMA 硬件可见

  // 只有线程 0 发出 TMA Store 命令
  if (threadIdx.x == 0) {
    auto gmem_coord     = tma_store.get_tma_tensor(shape(gmem_tensor));
    auto gmem_coord_cta = local_tile(gmem_coord,
                              Tile<Int<CTA_M>, Int<CTA_N>>{},
                              make_coord(blockIdx.x, blockIdx.y));

    auto tma_per_cta = tma_store.get_slice(0);
    copy(tma_store,
         tma_per_cta.partition_S(smem_tensor),       // 源：SMEM
         tma_per_cta.partition_D(gmem_coord_cta));   // 目标：GMEM 坐标
  }
  // kernel 退出时 TMA Store 会自动完成
}

TMA Store 的同步：内存围栏（Memory Fence）

TMA Store 不用 mbarrier，而是用一个「内存围栏」来确保顺序：

为什么不能用普通的 __threadfence_block()？ __threadfence_block() 不涉及「async proxy」（异步代理），而 TMA Store 运行在 async proxy 中。只有 tma_store_fence() 才能确保 SMEM 数据对 TMA 硬件可见。用错了会导致数据竞争（race condition），写出来的数据可能不对。

可选：TMA Store Arrive & Wait

如果 kernel 在 TMA Store 完成后还需要复用 SMEM（例如软件流水线），可以显式等待：

tma_store_arrive();    // 提交 TMA Store 操作（作为一个 cp.async.bulk-group）
tma_store_wait<0>();  // 等到最多 0 个操作待完成，即全部完成
// 现在 SMEM 可以安全复用了

如果 kernel 在发出 Store 后直接退出，这两行可以省略。

普通 TMA Store 是「赋值」：GMEM[tile] = SMEM。但有时我们需要「累加」或「取最大值」：

# 普通 Store：赋值
gmem[tile] = smem

# TMA Store Reduce 支持的操作：
gmem[tile] += smem          # 累加（用于 Split-K GEMM）
gmem[tile] = max(gmem[tile], smem)  # 取最大（用于 Attention）
gmem[tile] = min(gmem[tile], smem)  # 取最小

传统实现需要 3 步：读 GMEM → 计算 → 写 GMEM。TMA Store Reduce 把这压缩成 1 条 PTX 指令：

// 只需修改一行 host 代码，换一个操作类型：

// 普通 Store：
auto tma_store = make_tma_copy(SM90_TMA_STORE{}, gmem_tensor, smem_layout);

// 变成累加 Reduce：
auto tma_reduce_sum = make_tma_copy(SM90_TMA_REDUCE_ADD{}, gmem_tensor, smem_layout);
类比理解 就像把 a = b 换成 a += b，只改了一个「操作符」，其余代码完全不变。底层 PTX 指令从 cp.async.bulk 变成了 cp.reduce.async.bulk。

TMA Load Multicast：把同一块数据广播给多个线程块

在矩阵乘法（GEMM）等场景中，多个线程块需要 GMEM 的同一块数据。普通做法是每个线程块各发一次 TMA Load，但这样 L2 缓存命中率低。

Multicast（多播） 允许一次 TMA 操作把数据同时写入同一个「簇（cluster）」内多个 CTA 的 SMEM，保证 L2 命中。

Multicast 代码变化

主要有三处修改：

// 【Host 端】换用 Multicast 类型，并指定 cluster 大小（这里 z 方向有 2 个 CTA）
auto tma_load = make_tma_copy(SM90_TMA_LOAD_MULTICAST{},
                gmem_tensor, smem_layout, cute::_2{});  // ← cluster size = 2

// 同时调整 grid / cluster 维度：
dim3 grid_dims    = {M/CTA_M, N/CTA_N, 2};  // z 方向 2 个 CTA
dim3 cluster_dims = {1, 1, 2};             // cluster 包含 z 方向所有 CTA
// 【Kernel 端】三个关键变化：

// 1. 获取本 CTA 在 cluster 内的 ID（0 或 1）
uint32_t ctaid = cute::block_rank_in_cluster();

// 2. 位掩码：哪些 CTA 参与 multicast（0b11 表示 CTA 0 和 CTA 1 都参与）
constexpr uint16_t mcast_mask = (uint16_t(1) << cluster_size) - 1;

// 3. 用 ctaid 来切片，决定这个 CTA 负责加载哪一半数据
auto tma_per_cta = tma_load.get_slice(ctaid);   // ← 用 ctaid 而不是 0
copy(tma_load.with(tma_mbar, mcast_mask),        // ← 加上 mcast_mask
     tma_per_cta.partition_S(gmem_coord_cta),
     tma_per_cta.partition_D(smem_tensor));
关键理解：ctaid 决定加载哪一半 Multicast 时，get_slice(ctaid) 决定了每个 CTA 从 GMEM「切」哪一段数据写进自己的 SMEM。如果两个 CTA 都传 0，每个 CTA 的 SMEM 只有前半部分有正确数据，后半部分是 0；如果都传 1，则只有后半部分正确。只有 CTA 0 用 get_slice(0)、CTA 1 用 get_slice(1)，两个 CTA 才各自得到完整的数据。

Multicast 的额外同步

// Cluster 内所有 CTA 需要额外同步，确保屏障初始化完成后再使用
initialize_barrier(tma_mbar, 1);
__syncthreads();
cute::cluster_sync();          // ← Cluster 级同步
cutlass::arch::fence_barrier_init(); // ← 确保屏障初始化对整个 cluster 可见

// ... (TMA 操作) ...

wait_barrier(tma_mbar, 0);
cute::cluster_sync();          // ← 防止某个 CTA 提前退出

使用 TMA 的通用模式

  1. Host 端：用 make_tma_copy(SM90_TMA_LOAD{} 或 SM90_TMA_STORE{}, ...) 创建 TMA 对象，传给 kernel
  2. Kernel 端：用 __grid_constant__ const 接收 TMA 对象
  3. 线程 0：获取坐标视图 → 切出本 CTA 的部分 → 发出 copy() 命令
  4. 同步：Load 用 mbarrier 在之后等，Store 用 fence 在之前同步
